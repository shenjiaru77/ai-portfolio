# 第五周：本地部署入门 —— Ollama 部署笔记

> 本周主题：把 AI 装进自己的电脑
> 机器：Windows 11 / 内存 7.9 GB（≈8 GB）/ 无独立显卡
> Ollama 版本：0.40.6　　模型：qwen2.5:0.5b（397 MB）

---

## 一、安装与踩坑实录（按我实际遇到的写）

1. 打开 https://ollama.com/download 下载 Windows 安装包（`OllamaSetup.exe`），双击安装，一路下一步。
2. **坑①：装完在原来的 PowerShell 里敲 `ollama` 还是「不是内部或外部命令」**
   → 安装程序把 `%LOCALAPPDATA%\Programs\Ollama` 加进了 PATH，但**已经打开的终端不会重新读环境变量**。
   → 解决：关掉所有终端窗口重新打开；实在不行直接用完整路径：
   ```powershell
   & "$env:LOCALAPPDATA\Programs\Ollama\ollama.exe" --version
   ```
   （我这次就是在旧终端里一直报错，新开一个就好了——实测路径确实在 `C:\Users\shenj\AppData\Local\Programs\Ollama\ollama.exe`）
3. **坑②：`ollama pull` 卡住不动 / 超时**
   → 官方源在境外，校园网高峰时段会卡。解决：换手机热点重试；已下载的分片会续传，不用从头来。
4. **坑③：第一次 `ollama run` 等二三十秒没反应，以为卡死**
   → 那是在把模型装载进内存（我这边 26.56 秒才出第一个字）。之后的调用是「热调用」，3 秒左右就回。
5. **坑④：校园网/代理环境下，Python 连 `localhost:11434` 报 ConnectionError**
   → 代理设置会把 localhost 也送进代理。解决：`requests.Session().trust_env = False`（W6 的 `LocalEngine` 已经这么写）。
6. **坑⑤：Windows 终端里 Python 输出的中文是乱码**
   → 设 `$env:PYTHONIOENCODING="utf-8"`，并把控制台编码切到 UTF-8。

## 二、机器配置与模型选型

### 我的实测配置

| 项目 | 实际值 |
|------|--------|
| 内存 | 7.9 GB（≈ 8 GB 档） |
| 显卡 | 无独立显卡，`ollama ps` 显示 **100% CPU** |
| 所选模型 | `qwen2.5:0.5b`（397 MB） |
| 装载后占用 | 486 MB（`ollama ps` 实测） |

### 按内存选量级（选型参考）

| 内存 | 适合跑的量级 | 说明 |
|------|--------------|------|
| **8 GB** | **0.5B ~ 3B（4bit 量化）** | 推荐 0.5B–1.5B；3B 已经会明显挤占系统内存，纯 CPU 很慢 |
| 16 GB | 7B ~ 8B（4bit） | qwen2.5:7b、llama3.1:8b，约 4–5 GB，能流畅对话 |
| 32 GB | 13B ~ 14B（4bit），或 32B 激进量化 | qwen2.5:14b 约 9 GB；再大就慢到不适合课堂 |

### 为什么没选更大的

不是因为不想，是**硬件不允许**：

- 7B 模型 4bit 量化后约 4.5–5 GB，加上 Windows 本身 3–4 GB 常驻，8 GB 内存会开始**换页**（把内存写到硬盘），速度从约 30 token/s 掉到个位数。
- 没有独立显卡，全靠 CPU 推理，大模型只会更慢。
- 课堂演示的硬要求是「提问后 3–5 秒出结果」。0.5B 热调用实测 4–7 秒，刚好达标；换 7B 就变成几十秒，课上没法用。

**结论**：选 0.5B 是「8 GB + 无独显」条件下的稳妥解——**先保证跑得起来、演示不翻车，再谈质量**。质量不足的部分（见第四节）正好是第六周双引擎要解决的问题。

## 四、本地 vs 云端对比表（同一组 5 个学科问题）

> 云端说明：课程讲义模板用 **DeepSeek**；本机申请的是 **MiniMax**（同为 OpenAI 兼容接口）。
> 换成 DeepSeek 只需改 `BASE_URL` / `MODEL` 和密钥变量名三处，代码与结论不变。
> 本表为 2026-10-27 实测（本地 max_tokens=300；云端 Q1/Q3/Q5 用 1000，Q2/Q4 用 2500——原因见下方「一个真实发现」）。
> 注：同一问题多次运行，答案与耗时都会波动（CPU 负载 + temperature=0.7），下表取其中一次记录。

| # | 学科问题 | 本地耗时 | 本地质量（实测） | 云端耗时 | 云端质量（实测） | 隐私判断 | 该用哪个 |
|---|----------|----------|------------------|----------|------------------|----------|----------|
| 1 | 给《愚公移山》出 3 道 HSK4 阅读题 | 14.81 s | **差**：把「出阅读题」理解成「翻译题」，还编了原文没有的细节 | 13.98 s | **一般**：内容正确，但写成了故事复述，没按「3 道题」的要求输出 | 公开课文，可上云 | 云端，但**两边都要人工改** |
| 2 | 解释「把字句」的构成条件 | 14.94 s | **差**：把「把字句」说成「修辞手法」，完全答错 | 37.78 s | **好**：处置式、结构「主语+把+宾语+动词+补语」、构成条件都讲对了 | 通用语法点，可上云 | **云端**（本地已答错） |
| 3 | 把教案要点扩成完整教案 | 15.54 s | **一般**：套话模板，内容重复 | 3.88 s | **一般**：先追问要补充的信息，再给出完整教案结构 | 未公开教案 → 不上云 | **本地**（隐私优先） |
| 4 | HSK4 级对词汇量的要求是多少 | 5.39 s | **差**：说「1000 个左右」 | 26.18 s | **参考**：说「约 3000 词」（对应新版 HSK 3.0 口径，与课程讲义的旧版 1200 不一致） | 可上云 | **云端 + 必须查证** |
| 5 | 给中级汉语作文写三段式评语 | 15.11 s | **一般**：模板化、空泛 | 7.38 s | **好**：三段结构清晰，带可替换占位符 | 学生作文 → 不上云 | **本地**（隐私优先） |

### 一个真实发现：推理模型会「吃掉」max_tokens

第一次用 `max_tokens=300` 跑云端时，第 2、4 题返回的是**空字符串**。原因是 MiniMax-M2.7 会先输出一大段 `<think>` 思考内容，300 token 全被思考吃掉，真正回答一个字都没剩下的。
把它们提到 `max_tokens=2500` 后，才拿到完整答案（分别耗时 37.78 s、26.18 s）。

**教训**：推理型模型的 `max_tokens` 要按「思考 + 回答」一起算，不能只按回答长度给。
这也是第六周双引擎要打印耗时、并区分「快模型 vs 慢推理模型」的原因。

### 从表里看出的三个结论

1. **速度快 ≠ 能用**：本地 5–15 秒确实快，但第 1、2、4 题**直接答错**，快反而更容易误导学生。
2. **隐私决定下限**：第 3、5 题即使云端更好，也必须留本地——学生作文和未公开教案不能出本机。
3. **格式固定 + 人工可校验的批量活最适合本地**：单词表筛选、固定模板出题、离线演示；需要推理和质量的交给云端。
4. **具体数字两边都不可信**：第 4 题本地说 1000、云端说 3000、课程讲义说 1200（旧版口径）——这正好是第七周 RAG 要解决的问题：**让模型照着权威原文答，而不是凭记忆猜**。

> 复现方法：`python week05_LocalDeploy/compare_local_cloud.py`（会同时调本地与云端并打印表格；云端失败会标 ❌ 而不是回退本地）。

## 五、术语正名：量化 ≠ MCP

### 量化（Quantization）

把模型权重从高精度（如 16 位浮点）压成低精度（如 4 位整数），**模型体积和内存占用大幅下降、速度上升，代价是精度损失**。

常见后缀：`Q4_0`（4 位，最快最省）、`Q5_K_M`（5 位，质量稍好）、`Q8_0`（8 位，接近原始精度但更占内存）。

**一句话**：量化管「模型能不能装进你的机器」。

### MCP（Model Context Protocol）

一种让大模型**接入外部工具与数据**的通信协议（第 10 周专讲）。

**一句话**：MCP 管「模型能不能用外部工具」。

### 两者的区别

| | 量化 | MCP |
|--|------|-----|
| 解决什么问题 | 模型太大装不下 | 模型不会用外部工具/数据 |
| 作用层次 | 模型文件本身 | 模型与外部系统的连接 |
| 类比 | 把整箱书压缩成电子版 | 给模型装一个「工具箱接口」 |

**注意**：旧资料里「用 MCP 把模型塞进小内存」是**错的**——那是量化干的事，MCP 跟显存一点关系都没有。

## 六、隐私红线与上云前脱敏

### 不该上云的数据

- ✕ 学生作文、作业原件、成绩与评语
- ✕ 未公开的教案、试卷、校本题库
- ✕ 含姓名、学号、人脸、联系方式的任何材料
- ✕ 学校内部文件、未发表的研究数据

### 上云前怎么脱敏（三步）

1. **删直接标识**：姓名 → 「学生A」；学号、班级、电话、邮箱一律删掉。
2. **泛化间接标识**：学校名 → 「某校」；老师姓名 → 「老师A」；具体日期 → 「某天」。
3. **只留任务本身需要的语言材料**：如果是让 AI 改病句，就只保留句子，不保留「这是谁的作文」。

**示例**

- 原文：`初二3班 张小明（学号20231234）的作文：我的妈妈是一名医生……`
- 脱敏后：`学生A的作文：我的妈妈是一名医生……`

脱敏后仍要问自己一句：**这批数据出现在别人的服务器上，我会不会担责？会 → 留本地。**

## 七、盈亏平衡点

| 场景 | 推荐 | 理由 |
|------|------|------|
| 调用少、要质量 | 云端 | 按次付费比买硬件划算 |
| 调用多、要隐私、要离线 | 本地 | 边际成本≈0，数据不出门 |
| 批量出题、批量改写 | 本地 | 高频、格式固定、人工可校验 |
| 单次问答、临时任务 | 云端 | 质量高、不用等装载 |

## 八、常见排错

| 现象 | 原因 | 处理 |
|------|------|------|
| `ollama` 命令找不到 | 旧终端没重新读 PATH | 关掉终端重开，或用完整路径 |
| 下载慢 / 卡住 | 网络到官方源不稳定 | 换网络（热点）、重试续传 |
| 内存不足 / 电脑卡死 | 模型比内存大 | 换更小量级或更激进的量化 |
| `connection refused` | Ollama 服务没启动 | 运行 `ollama serve` 或启动 Ollama 应用 |
| Python 连不上 localhost | 代理劫持了本地请求 | `session.trust_env = False` |
| 中文乱码 | Windows 控制台编码 | `$env:PYTHONIOENCODING="utf-8"` |
| 第一次特别慢 | 模型装载中 | 属正常，热调用才代表真实速度 |

## 九、本周结论

1. 本地部署的门槛不在「懂技术」，在**硬件和网络**：8 GB 内存只能跑 0.5B–1.5B，且装完必须新开终端。
2. 0.5B 能跑通但**质量不可靠**——5 题里有 3 题答错（出题、把字句、词汇量），所以它只适合「格式固定、人工能校验」的活。
3. 量与质的取舍不是拍脑袋：**隐私红线 > 质量 > 速度**，这是第六周 `prefer` 参数的判断依据。
