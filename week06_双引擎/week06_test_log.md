## 原始证据（终端输出原文）

### 第 1 组：正常本地
```
[测试条件] prefer=local | max_tokens=800 | 问题=用一句话说明什么是把字句
[耗时] 26.56 秒（首次，含模型装载）
[结果] 成功
—— 热调用再跑一次 ——
[测试条件] prefer=local | 问题=用一句话说明什么是把字句
[耗时] 3.39 秒
[回答前300字] 把字句是一种修辞手法，其特点是通过改变词序和词性来增强语言的表达效果。
[结果] 成功
```
> 观察：本地 0.5b 热调用很快（3–4 秒），但质量明显不足——把字句是「处置式」，不是修辞手法。
> 这正是 W5 结论：本地适合格式固定、可人工校验的任务，不适合要质量的知识问答。

### 第 2 组：关掉 Ollama（回退证据，最关键）
```
[测试条件] prefer=local | 问题=用一句话说明什么是把字句
[首选引擎失败，自动切换] ConnectionError: HTTPConnectionPool(host='localhost', port=11435):
Max retries exceeded with url: /api/chat (Caused by NewConnectionError("... [WinError 10061] 由于目标计算机积极拒绝，无法连接。"))
[耗时] 8.24 秒
[回答前300字] 把字句是汉语中用“把”字将宾语提前到动词前，表示对宾语进行处置或操作的句式。
[结果] 成功
```
> 关键证据：`[首选引擎失败，自动切换]` 这一行证明本地失败后确实转向云端，
> 且云端答案质量明显更高——这就是「本地优先 = 自带兜底」的实证。

### 第 3 组：prefer='api'、云端不可用
```
[测试条件] prefer=api | 问题=用一句话说明什么是把字句
[首选引擎失败，自动切换] APIStatusError: Error code: 402 -
{'error': {'type': 'insufficient_balance_error', 'message': '当前已达到 Token Plan 用量上限...'}}
[耗时] 11.66 秒
[回答前300字] 把字句是一种特殊的句子结构，其中的每个词都是其前一个词的同义词或同音词。
[结果] 成功
```
> 观察：云端额度不足（402）时程序没有崩，而是对称回退到本地作答。

### 第 4 组：prefer='api'、云端可用
```
[测试条件] prefer=api | 问题=用一句话说明什么是把字句
[耗时] 3.17 秒
[回答前300字] 把字句是把宾语放在动词前面，用“把”引出动作所涉及的对象的句式，如“妈妈把书放好了”。
[结果] 成功
```
> 无切换日志，说明云端一次成功——`prefer='api'` 的正常路径成立。

### 第 5 组：max_tokens 调小（作业2 新增）
```
[测试条件] prefer=local | max_tokens=20 | 问题=用一句话说明什么是把字句
[耗时] 3.07 秒
[回答前300字] 把字句是一种语言表达形式，它通过将句子中的每个词或短语组合成
[结果] 成功
```
> 观察：回答在 20 token 处被硬截断，后半句直接消失。max_tokens 不是「建议长度」，而是硬上限。

## 作业 1 证据：失败重试（最多 2 次再回退）

```
[测试条件] prefer=local | max_tokens=800 | 问题=用一句话说明什么是把字句
[第 1/2 次尝试失败] ConnectionError: HTTPConnectionPool(host='localhost', port=11435): Max retries exceeded ...
[第 2/2 次尝试失败] ConnectionError: HTTPConnectionPool(host='localhost', port=11435): Max retries exceeded ...
[首选引擎失败，自动切换] ConnectionError: ...
[第 1/2 次尝试失败] RuntimeError: 未配置有效的 MINIMAX_API_KEY
[结果] 失败：RuntimeError: 未配置有效的 MINIMAX_API_KEY
```

> 说明：连接失败属瞬时错误，会重试一次；而「未配置密钥」属确定性错误，只尝试一次就放弃——
> 重试只对网络抖动/超时这类可能自愈的错误有意义，对 401/402/404 重试是浪费。
> 上例中云端密钥当时恰好是占位符，所以最终失败；换成真实密钥即会正常回退成功。

## 反思（作业2，约 200 字）

本地与云端的分工不是「哪个更强」，而是「数据能不能出去」和「任务要不要质量」。批改学生作文、写成绩评语、处理含姓名学号的材料，这些数据一旦上云就离开了我的控制，即使云端更准也必须走本地——隐私红线优先于答案质量。批量生成格式固定的练习题、课堂断网演示，本地小模型足够，还省了 token 费用。而复杂教案设计、多步推理、长文改写这类任务，本地 0.5b 明显答不准（本次把「把字句」说成修辞手法、把阅读题选项编错都是例子），交给云端更划算。拿不准时默认 local，因为失败会自动切云端，等于自带兜底。这样的分工既守住隐私底线，又不牺牲该有的质量。

---

## 结论

- **双向回退都真实发生**：本地挂 → 切云端（第2组）；云端挂 → 回本地（第3组），程序不崩。
- **本地优先 = 自带兜底**：课堂演示默认 `prefer='local'`，就算 Ollama 没开也不会翻车。
- **prefer 是判断不是随手填**：隐私任务走 `local`，复杂任务走 `api`；依据来自 W5 的选型笔记，是它的代码化。
- **质量差异真实存在**：同一问题，本地 0.5b 答错，云端答对——「快 ≠ 可用」再次得到验证。
- **max_tokens 是硬截断**：参数按任务给够，别指望模型自己收住。
